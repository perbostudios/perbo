# Product Experience and Onboarding

## First run

From the repository, run `./scripts/setup-local.mjs` (`node scripts/setup-local.mjs` on Windows). It checks Node 22+ and Git, fetches the pinned pnpm, installs dependencies, builds the CLI and the desktop, and opens Perbo; `--no-launch` builds without opening a window.

Inside Perbo:

1. Enter a name. It is stored on this machine and stamped on the tickets you admit — no account is created and nothing is sent anywhere.
2. Sign in to Claude Code and/or Codex through their own CLIs (`claude auth login`, `codex login`). Perbo runs on whichever subscription is already signed in and needs no API key ([D-093](11-open-decisions.md)). Choose executor and reviewer models, and each one's effort, from what each CLI reports.
3. Choose a repository already checked out on this machine — nothing is cloned. Run its environment check and save the proposed configuration; setup will not finish until that completes.

Re-running the setup script preserves your name, repositories and provider logins. The CLI it builds keeps tickets, contracts and evidence under `.perbo/` in whichever repository you point it at.

## The desktop

### Home and creating a task

Home lists the tickets the loop is carrying, and the right corner of its header counts them by colour, left to right: how many wait on your answer, how many stopped and how many completed, each only where there are any; the greeting beneath counts the tickets running and repeats the waiting and completed counts. Work before the loop — a planning, a spec, a plan not yet approved — is in **Create**'s picker, because approving is what starts the loop ([D-NEW-a-spec-outlives-its-planning](11-open-decisions.md)). With no tickets on it, the foot of Home says "Nothing admitted yet" at its left with a primary **Create a task** button at its right, the two on the page itself with no bar around them. Search (⌘K) matches title, key, branch or repository; filters narrow to what needs you (yellow), what's running (no colour), what's stopped (red) or what's completed (green); sort is newest, oldest, title or furthest along, and newest and oldest put yellow first, then red, then the rest. Archive all files every ticket on Home the loop has let go of, and says how many. Each card carries its stage, branch, repository and diff size (`+added −removed · files`, or "no diff yet" before a first run) — its ticket key shows as `#142`, with the `PRB-` prefix dropped. A card's colour says where its ticket stands: yellow where a finding waits on your answer mid-loop, red where the loop stopped and will not reach the end on its own, green where the journey ended — a pull request opened, merged or closed without merge, or a local run finished with no pull request to merge — and none anywhere else in the loop; the records being read again never changes it. The Home icon in the rail carries the same counts one colour at a time, in that order, each in its colour — a decision held seven seconds, a stop and a completion four — shrinking away and growing back as the next, unless your system asks for less motion; a colour with none is skipped, one colour alone stays still, and with none there is no count at all. A card whose next step is yours — an answer, a merge, a stopped run — carries the primary button. A card's buttons sit together at its right end, with Archive, an icon alone, always the last of them.

**Create** (⌘1; ⌘N too) sits first in the rail and opens a small picker: first each connected repository, to start planning there; under them the planning still open, with every plan drafted and not yet approved beside it and, under those, the specs your connected repositories hold that no planning and no ticket names, the way back into work whose plan is still to come, and Enter resumes the top planning still open. Opened from Home's empty state, the picker has nothing selected until an arrow key or the pointer picks a row. Picking a repository opens that repository's own page and creates nothing yet: the whole page beside the rail, where Create stays lit and no planning's panes are under it, and the question **What do you want to build?** over one wide box that says **Start planning** until you type and grows as your words wrap, with the repository and the chat's send button in its bottom-right corner. What you type there is kept for that repository as you type it, each repository keeping its own through going elsewhere and through closing Perbo, with the caret after it when you come back, and the picker opened from the page has that repository selected. Enter or the button starts the planning and sends what you typed as your first message to the Architect, exactly as the chat on the Spec pane would, clears what the repository kept and goes on to the Spec pane, where the chat shows it and the answer; Shift+Enter starts a new line, and an empty box sends nothing. A send that fails keeps your words and says why, and leaves no planning behind ([D-NEW-a-planning-starts-with-what-to-build](11-open-decisions.md)). Every piece of work the picker lists can be thrown away where it is listed — the repositories it offers to start in are not work and carry no bin — and each asks first in the words of the stage it is at. Deleting takes all of it, whatever stage it had reached: the planning, the ticket it drafted, the spec folder they came from and, for work that has run, its attempts and the evidence they sealed. One stage is refused: a ticket whose pull request is open, which is a record outside this machine — close or merge it on GitHub and the delete is offered again. The spec is left only where something else still names it — another planning writing the same file, or another ticket drafted from it ([D-NEW-a-spec-outlives-its-planning](11-open-decisions.md)). Planning mode holds one piece of work in one repository ([D-101](11-open-decisions.md)); its panes sit under Create in the rail while it is open, and Home, Archive and Settings leave it, with the draft kept as a contract editing session that survives a restart. A planning reopens on the pane you left it at, whether you went Home or closed Perbo — from the picker, from the ticket's own page and from the contract's **Back to planning** alike — unless that pane is no longer there to open, such as a Graph for a plan put back into one piece, and then it opens where it otherwise would; while problems are open, the picker and the ticket's own page open it on them instead, though the contract's way back still goes where it was left, and the reading on the way to the contract is never where it reopens. Left at the contract of a plan still waiting for approval, it reopens on that contract, from the picker, the ticket's own page and after a restart, until you go back into the planning; once the plan is approved the ticket opens where its state is, and a stopped run on its stopped page ([D-NEW-a-planning-reopens-where-it-was-left](11-open-decisions.md)). A planning you opened and put nothing into — no title, no spec, no message in the chat, no plan — is thrown away as you leave it, so clicking away from one you opened by mistake leaves nothing behind for the picker to offer; anything you have put into it stays, and closing Perbo is not leaving it: an untouched planning is still there when you come back ([D-NEW-a-spec-outlives-its-planning](11-open-decisions.md)). Its Spec pane holds the spec ([D-103](11-open-decisions.md)): a title and the five sections — Outcome, Requirements, No-Gos, Rabbit holes and Notes — each saved into the repository at `specs/<slug>/spec.md` when you leave it, with the folders created the first time. The slug comes from the title; a planning you have not titled takes one from your first message to the Architect, which the chat says as it names the folder, and the Architect is asked to give the spec a title of its own as it first writes it ([D-118](11-open-decisions.md)). Once a plan is drafted the spec's title is the ticket's name, and renaming a ticket still being planned renames its spec with it; the folder keeps its name ([D-NEW-a-ticket-is-named-apart-from-its-board](11-open-decisions.md)). Each requirement is given an id when it is saved, and beside each id is the node its criteria sit in, or *none yet* before there is a plan — the requirements themselves are read in the section you write them in rather than listed again under it. The file is the spec: between one save and the next the repository holds it, so a spec you edited in your own editor is what the pane shows the next time it reads. Type `@` to name code and the pane offers the repository's exported names, with what each one is and the file it lives in; choosing one writes it in. Every `@name` is marked as you write, one the index does not hold is marked apart, and under the section it offers the two nearest names, each replacing every use of it there. The head says how many do not resolve, and says when there are no names to check at all; how many the index holds and the commit it was built at are behind the **i** beside them, as is the reason it is not built where it is not ([D-015](11-open-decisions.md)). The Architect writes this same file too: your save never overwrites a section it did not read, so where the Architect changed a section you also changed, your save is refused, both texts are shown, and you keep yours, take the file's, or keep both — nothing else in the spec is written until you have. The Architect writes through its own tools rather than this check, so what it does with a section you changed after it last read the file is the Architect's own behaviour. It writes the spec and stops there — it holds no tool that drafts a plan — so generating one is always your press, and there is one place to make it: **Generate plan**, which appears at the foot of this pane once the spec has a title and an outcome, under the spec it drafts from. It is withheld while a group of its questions is still in front of you, because your answers change the spec it would draft from. Pressing it while the Architect is still talking is one press for both: it stops the Architect and drafts from the spec that turn left behind, so you never stop the conversation by hand and then press again. A spec the drafter refuses is said on this pane in the drafter's words, and the next press drafts again. The chat is headed **Chat**: before the plan it questions you and writes the spec, and after it every turn changes the spec and the plan together, with the conversation from before the plan folded behind one line at the top of it — **Show the earlier chat** opens it and **Hide the earlier chat** folds it again. **Generate plan** drafts the contract and its execution graph from it and lands you on the plan — the **Graph** pane for work the drafter divided, the **Plan** pane for work it did not, which is that work's acceptance criteria and the whole of what there is to check before confirming; after that the plan changes by editing it, and **Start over from the spec…** asks first and then drafts the same task again, dropping the plan edits made since and keeping everything in the spec. A spec written in the chat is how a plan is made here, so neither this pane nor any other screen offers a second way to start one: the Architect asks about the work, the spec states it, and the plan is drafted from the spec. A contract `admit --from-file` drafted at the terminal for work that never had a spec opens in the same criteria editor, reached from the task itself. Either way you land on the compiled contract before anything runs, with as many criteria as the work has, each pairing what must be proven with the assertion that proves it (test, query, metric or artifact), and an assertion the draft did not propose marked as changed since it, because approving freezes what will be taken for proof and a criterion whose assertion moved reads exactly as it did, and an allowed scope of path globs with headroom for a few files beyond them; paths the repository always refuses stay listed and out of reach. Its **Graph pane** holds the execution graph ([D-100](11-open-decisions.md)): the nodes laid out left to right by the order between them, each with its title and its criteria, the paths expected to satisfy them being in its inspector, and the plan's size beside them — S to XL, with the four counts it comes from and the ones that set it ([D-104](11-open-decisions.md)) — recomputed after every edit. Drag the canvas or scroll to move a large graph around with a node open, and pinch on a trackpad, or scroll with ⌘ or ⌃ held, to zoom it about the pointer. Add a node, split one in two, merge two, delete one, edit a criterion or a node's paths, and draw or remove an edge; every one of those goes through `perbo edit --graph-edit`, the one path a plan changes through, so each is validated whole, recorded with who made it and undoable — the pane lists them with an Undo on the latest. A criterion may not cite a requirement the spec does not carry, which approving refuses; otherwise the plan may be arranged and reworded any way at all, and none of it asks you to touch the spec. The Architect is held to more, because it is the one editor holding both documents: when it changes what the plan promises — the outcome, or a criterion's own words — it writes the spec in the same turn or the edit is refused. So a hand edit — here, in the spec, or in your own editor — can leave the plan and the spec disagreeing, and so can a chat turn that writes the spec and leaves the plan alone. When either has, the way from the plan to the contract reads the two against each other: a model reads the spec's outcome and requirements beside the plan's outcome and criteria and says where the words no longer promise the same thing, and only that — never how the plan is arranged or how a criterion is proven. Where it finds any, a **Problems** page sits in the rail after Impact while they are open; resolved, it is only the step every Confirm passes through. It puts the problems to you one at a time, with a count in its corner — **Problem 1 of N**, **N more after this** — each a card in the chat's own shape with the ways to close it to pick from and **Something else**, which opens a box on the card for your own words, and the bar at the card's foot puts what you picked or said to the Architect as your turn, so the spec and the plan move together under the same rule; the page says **Resolving the problem** while the Architect applies your answer and the plan is read against the spec again, and the next problem appears once that reading finds it still there. The same problem is also a card in the chat, headed the same way, so from the Graph or the Impact pane you answer it there, and the chat carries your answers either way. Once every problem is resolved the page says so and offers **Confirm the plan** at its foot, to the right of **Back to the plan** — the work is still being planned, and the button is the way on to the contract — and the chat's note saying so carries the same button. A question the Architect asks of its own stands ahead of that: the page shows it as the thing to answer, headed **A question from the Architect** with the count hidden, and neither the page nor the chat offers the way on until you have answered it and the plan has been read against the spec again. It is advice: **Go on to the contract anyway** leaves every problem open and is remembered, so the same reading is not put to you again until one of the two moves; **Back to the plan** returns you to it. A plan just drafted, a plan rearranged, a plan the chat moved from a clean state and problems you resolved from another pane pass straight through to the contract ([D-NEW-the-plan-answers-the-spec-and-says-so](11-open-decisions.md)). Selecting a node opens it under the canvas in two equal halves: its criteria, which scroll on their own, and beside them one block that stays put, holding what it comes after and before side by side, then its paths, then, read-only, the Notes written on the page generated for it beside the spec — the one part of that page a person writes, the rest being what its card already shows. A dotted **+ path**, **+ after** or **+ before** chip at the end of each row adds to it: the path chip opens a box that takes a path or glob on Enter, the order chips a list of the other nodes. Once the loop is running the same pane is where you watch it: each node the change touched carries one word for where it stands — changed, checks passed, checks failed, covered by review, or a finding open — with the changed paths inside its own globs under it, and the chip says which record the word came from; a node with none of these on record carries none. Opening a node adds, under each criterion, whether the review met it, how it was established, where the evidence is and any finding still open against it. Changed paths that no node's globs match are listed together as changed outside every node, because work nobody planned for is worth seeing rather than dropping; a flat plan has no node for a path to be outside of and lists none. All of it comes from the sealed change set, the pinned checks run per node and the review artifact, and none of it from what the agent said about its own work ([D-100](11-open-decisions.md), [D-107](11-open-decisions.md)). Every step between the spec and the loop that runs a command says so while it runs, in the same words and the same manner: drafting the plan from the spec, reading the plan against the spec on the way to the contract, compiling the contract on the way to the page that freezes it, and approving it before the loop starts. A step inside planning, such as the reading, keeps the rail beside it, because the planning is still there; a step that is the whole of what is happening takes the window. **Confirm the plan** (⇧⌘↵) says the division is right and takes you through that reading — every way from the plan to the contract goes through it, the shortcut included — to the contract, where approving freezes the outcome, each node's criteria and paths and the base, and starts the loop. It waits while the Architect is mid-turn, and says it is waiting, because a turn in flight may still be moving the plan and what freezes is what the contract holds when it is read. One contract has one approval, on the screen that says what it freezes, and on a plan already approved the same button reads **Open the contract**. **Start over from the spec…** asks first, as the Spec pane does. The pane also opens for a ticket already in `plan_review`: the picker lists it under Continue planning. Its Explorer pane lists the repository's tracked files, previews one read-only with line numbers, and is where you mark a path for this draft: **allowed** adds it to the scope, **prohibited** keeps executors out even inside the allowed paths, and **Always prohibit in this repository** is a checkbox with no confirmation that puts the path on the repository's standing list, for every ticket here ([D-105](11-open-decisions.md)). Every mark is listed with an undo, and an entry someone else put on the standing list is shown locked with where it came from. Perbo reads code and never edits it ([D-015](11-open-decisions.md)), and paths that may hold a secret, Git metadata or agent configuration are neither listed nor read; the pane says how many it withholds. Its **Impact pane** lists what this draft is likely to touch that its scope does not cover ([D-015](11-open-decisions.md)): files outside the scope that import what the draft changes or what the spec names, and paths in one of the classes Perbo recognises — a migration, a dependency manifest, configuration, something security-sensitive, CI, infrastructure or policy — inside a package the scope or the spec reaches. It checks once on its own, when the planning first has a plan, because a plan is what impact is measured against; asking again after that is yours — **Check impact** before there is an answer and **Check again** after one, each a fresh index of the whole tracked tree — and the pane says what it was checked against and when. The count also sits on the contract page, beside the scope it is about, because that is the page where approving freezes the scope and so the last place a warning can still be acted on; it says how many files fall outside and opens them, and it never holds the Approve button — a warning that gated approval would be one people learn to click past. It is shown only where there is something to say. Every warning is advice, and nothing it says reaches the plan on its own. **Add to scope** makes it the same mark the Explorer makes, listed in the draft's history with an undo; **Add as a No-Go** appends one line to the spec's No-Gos section, which is the file the Spec pane reads back, and says it once however often you ask. A repository with no tracked TypeScript or JavaScript gets the path classes alone, with a sentence saying nothing there read an import and which extensions it does track; the paths the Explorer withholds never appear here either. Beside whichever pane is open sits the **Chat** ([D-102](11-open-decisions.md)): your own Claude Code or Codex session, in a dock that does not collapse — the Problems page alone is without it — though the bar on its edge drags it wider or narrower — by the pointer, or by the arrow keys once it has focus, with Home returning it to the width it opens at — and what you set it to is remembered on this machine; with the conversation, one status line under the last message saying what the turn is doing — reading what you said, thinking, writing the spec, changing the plan — for as long as it owes you a word, through the pauses it takes mid-answer, giving way to **The Architect**'s bubble with its dots while a line it has said is held back on its way to you, and only then, and gone once the next word is yours, or once it has stopped or been stopped ([D-119](11-open-decisions.md)), a box to type your turn into, sent with Enter or the round arrow in its bottom-right corner, muted until there is something to send, whose rim pulses while it waits on words only you can type, and a stop. It reads anything, writes only this spec's folder, `CONTEXT.md` and the ADR folder, and cannot approve, publish or merge; a command it may not run and a write it may not make are each shown as **refused**, with the rule that refused it and nothing to allow or deny — the session is never asked to allow anything and never asks you to. It asks you about the work itself, and what it cannot settle from the repository, the spec or what you have already said comes with the answers to pick from: one group at a time under the conversation, in a card with a size of its own — the bar on its top edge drags it taller or shorter, by the pointer or by the arrow keys, and what you set it to is remembered on this machine — its answers scrolling inside it with the next one cut off at the edge so you can see there is one; parts lettered together where one answer depends on another, the session's own recommendation first where it made one, and every part carrying two answers of its own side by side: **Something else** on the left, which opens over the other into a box for that part, closed again by picking **Something else** again with what you typed kept, with the group's other parts still there to pick, and leaving it as the Architect's call on the right. While a group is in front of you the box under the conversation is not — every answer it wants is on the card, your own words included — and nothing goes as you pick or type: a bar across the card's foot, the round arrow at its right, sends the whole group together as your turn once every part is either picked or said, a line a part in the option's wording or yours, a pick clicked again being taken back and the arrow keys moving a pick without making it until Enter or Space does ([D-117](11-open-decisions.md)). Words of your own on a question of one part are a sentence like any other and take the rest of the questions off, since the Architect answers what you said; the line in the conversation that says they were asked keeps them: hover or focus the **i** beside it and they are there. Each card the chat keeps for its own tools is one line — **Changed the plan**, or **Changing the plan** for a change that was refused — one that worked carrying the same **i**, so what a tool wrote is one hover away rather than filling the dock; a refused call adds one short line under its name, the first sentence of why, and a refusal shows its reason without asking, because that is the thing to act on. A change it makes to the plan goes through the same validated edit path your own edits go through, and the chat carries what is said nowhere else: an undo, a refusal, and the plan edit the **Undo** is still offered on, as one line with the **Undo** on it, because what the edit changed is on the graph and in the spec, where you read it. An edit behind that one has no card, because the graph already holds what it changed. A moment after the spec's write lands — while the session is often still composing — a line says the spec is written and is yours: read it and change it on the Spec pane, ask for a change here, or press **Generate plan** at the foot of that pane. The line names that press rather than carrying one of its own, because what you do next is yours to decide, and for the rest of that turn nothing under it says the session is working, and what the session says after it is not shown. A turn that changed the spec as well as the plan says so in one line, marked to be read: the spec is on another pane, and a person watching the chat would otherwise not find out that half of the change landed there. **History** opens the plan's every change as a drawer over the pane, so the chat stays where it is: each entry labelled you or The Architect, with an undo on the latest still in force. After every change to the pair — the chat's, a hand edit's, an answer to a problem — what changed in the spec and the plan is marked where you read them, additions highlighted green, one unbroken highlight across words added together, and removals red and struck through: in the Spec pane's reading, on the Graph's node cards and in its inspector, and on the Plan pane; a criterion the change added is wholly green, one it removed is shown struck at the end of the list, and a section or a criterion you are editing shows no marks. Only the last change is marked: the next one turns those marks back to plain text and marks its own. The first words written into an empty box are not a change to it, so a spec section the Architect or you write for the first time and a plan just drafted show no marks; a later edit of those words does. The provider and model are this planning's drafting choice, and the chat is the same chat on either. The conversation is kept with the planning, so leaving planning mode and restarting the app both come back to it, and the Architect keeps running until you stop it — sending a turn after that starts it again on the same session, which continues the same conversation. Contract edits in progress are saved on the device and restored if you leave and come back ([D-095](11-open-decisions.md)); the spec's own text lives in the repository instead, and the session remembers which spec it is writing. Planning runs alongside a run: you can draft, save and compile a contract while a loop is going, and while one is going elsewhere. Starting a run, answering a decision, recording a finding, refreshing delivery, recording a product decision and checking a repository each take one at a time, and asking for a second says which one is in the way; disconnecting a repository, deleting a contract or changing its manifest waits for every command running in that repository ([D-101](11-open-decisions.md)).


### The contract editor and approval

The contract shows the outcome, each criterion with its expected evidence, the allowed and prohibited paths, the base commit, the executor and reviewer models, each with its effort — each chosen here, because they are not among the four fields approving freezes and this is the last page before the loop starts; they read as stated text once the contract is approved — up to three engineering skills for the executor ([D-094](11-open-decisions.md)), and what stops this run — the stall window, the fact that nothing bounds its time, tokens or commands, and the ticket cost cap that applies only to an executor billed per token ([D-096](11-open-decisions.md)). Approving freezes four fields — outcome, criteria, scope, base — for good; how the work gets done stays the agent's. A checkbox asks whether to push the branch and open a pull request once the review gate passes; you still merge it yourself. Approving here is exactly `perbo approve`, run for you before the loop starts. It can be deleted here as a piece of work is from the picker, behind a confirmation that says what goes with it ([D-NEW-a-spec-outlives-its-planning](11-open-decisions.md)). **Back to planning** returns to the planning curating this ticket — the pane it was left at, or the plan ([D-NEW-a-planning-reopens-where-it-was-left](11-open-decisions.md)) — and, for a contract no planning curates, to the ticket's own editor, because not being ready to approve means going back to change the plan; the spec is read and written in planning, and this page offers no second door to it.

### The run view and the review result

The loop screen names what's happening now against six stages — contract, execution, checks, decisions required, refinement, review — with a running description of steps taken and a strip of commands used, cost spent and files touched beside the stall window that would stop it; no time estimate is invented. From here you can open the worktree in your editor, stop the loop, or watch the agents' own output: a transcript of executor and reviewer turns, a terminal pane, and the changed files — recorded output, not evidence. The reviewer never reads the executor's narrative. A run you stopped lands on a page of its own: at once from **Stop the loop**, without waiting for the stop to settle, and from Home, or from the Archive once it is filed, for as long as the ticket is stopped. The page holds the ticket's name, that the run was stopped, and the three things the records allow as buttons named and described nowhere, in one row at the bottom left — **Delete this work**, **Plan it again** and **Continue the task**, the last darkened — with **Open the contract** and **Watch what the agents did** at the right end of the same row, so nothing on it scrolls. **Continue the task** is another attempt against the same approved contract, carrying on from the last attempt's retained changes where it sealed any and starting the attempt again where it did not; it publishes as the stopped run was going to, by the contract page's checkbox, so nothing is asked again ([D-NEW-a-spec-outlives-its-planning](11-open-decisions.md)). **Plan it again** puts the work back before the loop: the approved contract is frozen ([ADR-0016](adr/0016-minimal-machine-maintained-planning.md)), so the stopped ticket is deleted with everything recorded after its contract — its attempts and the evidence they sealed — and leaves Home at the click, the spec it was drafted from stays, a new plan is admitted from it, and you land in planning on the new plan's Graph, or on its Plan pane where the drafter did not divide it, with the work in **Create**'s picker as planning to continue; where the plan cannot be drafted once the ticket is deleted, you are told the ticket was deleted and that its spec is in **Create**'s picker to draft the plan from; it is offered for work drafted from a spec, and the spec has to still be there — a spec deleted since is said so, in the words the command itself refuses in. A run stopped outside the executor's window leaves the ticket stranded at the stage it reached, and a spec whose ticket is still live has its plan, so the button is disabled where the record is not spent, and says why only when you hover it; a ticket whose pull request is open is not offered it, because it is not deleted. **Delete this work** removes all of it, behind a confirmation — at every stage but one: a ticket whose pull request is open is refused, because that pull request is a record outside this machine, and it is closed or merged on GitHub first. A stop leaves the record where it stood — sealed at failed inside the executor's window, stranded at the stage it reached outside it — and none of these three changes that.

Once the gate closes, the review screen shows each criterion's verification strength and evidence location, the deterministic checks, and any open findings, with cost and elapsed time beside them; you can send a finding back for another look, export the evidence, or return to the contract to retry. If a pull request was authorized, the merge screen asks one question — merge or don't — with the verified-criteria count, the checks, the scope and the base commit beside it; the desktop opens your browser to GitHub and never merges the pull request itself. Either way the ticket returns you to Home with what changed.

### Completed tickets and the archive

A ticket stays on Home, marked complete, once it merges or closes — nothing files it away on its own. Archiving it, one at a time or all at once, moves it to the Archive: a searchable, filterable, sortable table with a diff column and CSV export, and a ticket filed by mistake returns to Home in one click. A stopped ticket deleted from its page, reached from Home or the Archive, leaves both lists at the click and does not come back while the delete finishes. A ticket whose run stopped is archived the same way, one at a time; one the loop still carries — running, or waiting on a decision, a merge or the queue — cannot be ([D-097](11-open-decisions.md)). The table fills the page with its count and pages under it, and shows no rows rather than a message when nothing matches.

### Settings, shortcuts and themes

The settings icon opens a pill of three sections. **General** holds your name, what can interrupt you and how (below), appearance — light, dark or system; text size; reduced motion — and AFK mode, which holds the machine awake for as long as a run or a decision is live. **Usage** answers whether you can start another ticket: each connected provider's own plan windows where it reports them, and this machine's ledger — spend this month, tickets run and tickets stopped short, average cost per merged ticket — read from retained attempt records, with unpriced attempts marked rather than guessed. **Connections** holds provider sign-in and refresh, the default model and effort per role, which a contract's choices start from, what stops a run on this machine — the stall window and the per-token ticket cost cap, which can tighten a repository's own limits and never loosen them — and repositories with their environment check and off-limits paths.

Every keyboard binding is rebindable per machine from Settings → General → Shortcuts: click one and press the new combination; a combination already in use is refused and named rather than silently taken. Approving a contract and opening a pull request stay fixed, since they are the two actions that spend money or write to your repository.

Decided, not built: a phone companion once pairing lands ([D-097](11-open-decisions.md)).

### When the loop interrupts you

The loop pauses for you only on a real decision — never for routine progress. One question at a time, with its evidence and, where the executor offered them, a few concrete options plus "let it decide" or your own words in a sentence; every answer stays editable until you confirm the whole set, and confirming resumes the run. Outside a live decision, Perbo only notifies on four things — a decision is needed, a review finishes, a run stops short (it stalled, or hit a ceiling the repository set), or any stage changes — never on progress alone, and never twice for the same fact.

## The same work, from the command line

Everything above has a `perbo` command behind it, for scripting or a repository with no desktop open.

- **`perbo admit`** — one piece of work into a ticket and its contract, in `plan_review`. Type `--outcome`, `--criterion` and `--path` yourself, or let a model draft them from a GitHub issue (`--from owner/repo#412`) or a Markdown file (`--from-file issue.md`). Nothing runs until the draft is approved.
- **`perbo edit PRB-142`** — open the contract in `$VISUAL`/`$EDITOR`, or pass `--outcome`/`--criterion`/`--path` to change one part directly. Only while the ticket is in `plan_review`.
- **`perbo approve PRB-142`** — freezes the contract from that moment.
- **`perbo run --ticket PRB-142 [--publish]`** — provisions a worktree, executes, seals the change, runs the pinned checks, reviews independently, routes remediable findings back to the executor, and with `--publish` opens the pull request. A person still merges it.
- **`perbo inspect PRB-142 [--attempt <id>]`** — every attempt read back: how it ended, cost, checks, the review and where each finding went; `--verify` recomputes an attempt's stored hashes instead of reading it.
- **`perbo list [--all]`** — the admitted work and where each ticket stands.
- **`perbo sync PRB-142 [--merge]`** — reads the pull request, its checks and its stop answers from GitHub onto the ticket; `--merge` additionally merges it, but only where the repository has opted into `merge: loop` and a separate review run has approved that exact head ([D-041](11-open-decisions.md)).
- **`perbo stops`** — precision of stopping, read live from the answers on pull requests: of the changes with an answer, the share a person endorsed, beside the share of changes a person was shown anything on, and beside it the share of merges that went out unattended.
- **`perbo escapes`** — of the tickets that merged: how many were reverted, and how many separately had a touched path changed again within fourteen days.
- **`perbo serve`** — the queue over the ticket store. Each tick it fetches the base, syncs and, where configured, merges open pull requests in dependency and priority order, starts ready tickets up to the configured concurrency, and drafts tickets from a tracker label if one is configured. While it runs it hosts a local endpoint for your own session.
- **`perbo agent [--provider claude|codex]`** — your own Claude Code or Codex session in the checkout, with that endpoint injected. That session can read every ticket and its evidence, admit new tickets as drafts, edit an unapproved contract, sync a pull request and pause the queue — never approve, publish or merge; that stays a person's keystroke. Needs a running `serve`.
- **`perbo interview --spec specs/<slug>`** — your own session, Claude Code through the Claude Agent SDK or Codex through `codex app-server`, questioning you about a piece of work and writing the spec. It reads anything and runs read-only commands; the spec folder, `CONTEXT.md` and the ADR folder are the only places it writes, and anything else is refused rather than put to you — on Codex the app server's own approval questions are answered by the same rules rather than reaching you. It writes the spec, and once you have drafted the plan from it, changes that plan only through the validated edit path, recorded as the Architect's; it cannot approve, publish or merge ([D-102](11-open-decisions.md)). The desktop starts it on Claude Opus 5.5 wherever Claude Code's catalog offers that model, and otherwise on the planning's drafting model.
- **`perbo principle add "..."`** — records a product answer no established practice could settle; every later executor brief consults it. This is what the desktop's decision screen writes on your behalf when you answer one.

## What you see, and what the loop handles

The loop is the product; independent review is one step inside it, not the thing you interact with directly ([D-088](11-open-decisions.md)). Admitted work runs end to end — execution, checks, review, repair — and a person sees only what needs a decision ([D-001](11-open-decisions.md)). Every finding the executor can close against an established practice, it closes without you; only a `security.*` or `context.*` finding, a deterministic check that failed, the final remediation round, or a point the executor declares it has no practice for reaches you, in the desktop's decision screen or a pull request's checkboxes ([D-065](11-open-decisions.md)). A person picks the model and provider for Perbo's own review ([D-088](11-open-decisions.md)). Decided, not built: reviews other tools leave on the same pull request are read and routed like Perbo's own findings.
