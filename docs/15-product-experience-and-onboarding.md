# Product Experience and Onboarding

## First run

From the repository, run `./scripts/setup-local.mjs` (`node scripts/setup-local.mjs` on Windows). It checks Node 22+ and Git, fetches the pinned pnpm, installs dependencies, builds the CLI and the desktop, and opens Perbo; `--no-launch` builds without opening a window.

Inside Perbo:

1. Enter a name. It is stored on this machine and stamped on the tickets you admit — no account is created and nothing is sent anywhere.
2. Sign in to Claude Code and/or Codex through their own CLIs (`claude auth login`, `codex login`). Perbo runs on whichever subscription is already signed in and needs no API key ([D-093](11-open-decisions.md)). Choose executor and reviewer models from what each CLI reports.
3. Choose a repository already checked out on this machine — nothing is cloned. Run its environment check and save the proposed configuration; setup will not finish until that completes.

Re-running the setup script preserves your name, repositories and provider logins. The CLI it builds keeps tickets, contracts and evidence under `.perbo/` in whichever repository you point it at.

## The desktop

### Home and creating a task

Home lists the tickets Perbo owns, with a count of what needs you and what has completed. Search (⌘K) matches title, key, branch or repository; filters narrow to what needs you, what's running or what's completed; sort is newest, oldest or title. Each card carries its stage, branch, repository and diff size (`+added −removed · files`, or "no diff yet" before a first run) — its ticket key shows as `#142`, with the `PRB-` prefix dropped. A ticket needing you is marked and carries the primary button.

**Create** (⌘1; ⌘N too) sits first in the rail and opens a small picker: planning still open is listed first and Enter resumes the top entry, and below it each connected repository starts planning there. Planning mode holds one piece of work in one repository ([D-101](11-open-decisions.md)); its panes sit under Create in the rail while it is open, and Home, Archive and Settings leave it, with the draft kept as a contract editing session that survives a restart. Its Spec pane holds the spec ([D-103](11-open-decisions.md)): a title and the five sections — Outcome, Requirements, No-Gos, Rabbit holes and Notes — each saved into the repository at `specs/<slug>/spec.md` when you leave it, with the folders created the first time. The slug comes from the title; a planning you have not titled takes one from your first message to the interview, which the chat says as it names the folder ([D-118](11-open-decisions.md)). Each requirement is given an id when it is saved, and beside each one is the node its criteria sit in, or *none yet* before there is a plan. The file is the spec: between one save and the next the repository holds it, so a spec you edited in your own editor is what the pane shows the next time it reads. Type `@` to name code and the pane offers the repository's exported names, with what each one is and the file it lives in; choosing one writes it in. Every `@name` is marked as you write, one the index does not hold is marked apart, and under the section it offers the two nearest names, each replacing every use of it there. The head says how many do not resolve, beside how many names the index holds and the commit it was built at; a repository with no TypeScript or JavaScript says so and marks none apart ([D-015](11-open-decisions.md)). The interview writes this same file too: your save never overwrites a section it did not read, so where the interview changed a section you also changed, your save is refused, both texts are shown, and you keep yours, take the file's, or keep both — nothing else in the spec is written until you have. The interview writes through its own tools rather than this check, so what it does with a section you changed after it last read the file is the interview's own behaviour. **Generate plan** drafts the contract and its execution graph from it and lands you on the plan; after that the plan changes by editing it, and **Start over from the spec…** asks first and then drafts the same task again, dropping the plan edits made since and keeping everything in the spec. Under the document the pane keeps the contract steps it has always had, for work that never had a spec: one sentence for the outcome, and the executor and reviewer models (your defaults, changeable for this task). From there you either write the acceptance criteria yourself or have a model draft them from what you wrote — through the same path `admit --from-file` uses for a real issue, so what comes back is proven against your outcome rather than restating its title; drafting spends against your subscription, writing them yourself does not. Either way you land on the compiled contract before anything runs, with as many criteria as the work has, each pairing what must be proven with the assertion that proves it (test, query, metric or artifact), and an allowed scope of path globs with headroom for a few files beyond them; paths the repository always refuses stay listed and out of reach. Its **Graph pane** holds the execution graph ([D-100](11-open-decisions.md)): the nodes laid out left to right by the order between them, each with its title, its criteria and the paths expected to satisfy them, and the plan's size beside them — S to XL, with the four counts it comes from and the ones that set it ([D-104](11-open-decisions.md)) — recomputed after every edit. Drag the canvas or scroll to move a large graph around with a node open. Add a node, split one in two, merge two, delete one, edit a criterion or a node's paths, and draw or remove an edge; every one of those goes through `perbo edit --graph-edit`, the one path a plan changes through, so each is validated whole, recorded with who made it and undoable — the pane lists them with an Undo on the latest. Selecting a node opens it under the canvas with its criteria, its paths, what it comes after and before, and the page generated for it beside the spec, read-only. Once the loop is running the same pane is where you watch it: each node carries one word for where it stands — untouched, changed, checks passed, checks failed, covered by review, or a finding open — with the changed paths inside its own globs under it, and the chip says which record the word came from. Opening a node adds, under each criterion, whether the review met it, how it was established, where the evidence is and any finding still open against it. Changed paths that no node's globs match are listed together as changed outside every node, because work nobody planned for is worth seeing rather than dropping; a flat plan has no node for a path to be outside of and lists none. All of it comes from the sealed change set, the pinned checks run per node and the review artifact, and none of it from what the agent said about its own work ([D-100](11-open-decisions.md), [D-107](11-open-decisions.md)). **Approve** (⇧⌘↵) freezes the outcome and each node's criteria and paths and starts the loop, and **Start over from the spec…** asks first, as the Spec pane does. The pane also opens for a ticket already in `plan_review`: the picker lists it under Continue planning. Its Explorer pane lists the repository's tracked files, previews one read-only with line numbers, and is where you mark a path for this draft: **allowed** adds it to the scope, **prohibited** keeps executors out even inside the allowed paths, and **Always prohibit in this repository** is a checkbox with no confirmation that puts the path on the repository's standing list, for every ticket here ([D-105](11-open-decisions.md)). Every mark is listed with an undo, and an entry someone else put on the standing list is shown locked with where it came from. Perbo reads code and never edits it ([D-015](11-open-decisions.md)), and paths that may hold a secret, Git metadata or agent configuration are neither listed nor read; the pane says how many it withholds. Its **Impact pane** lists what this draft is likely to touch that its scope does not cover ([D-015](11-open-decisions.md)): files outside the scope that import what the draft changes or what the spec names, and paths in one of the classes Perbo recognises — a migration, a dependency manifest, configuration, something security-sensitive, CI, infrastructure or policy — inside a package the scope or the spec reaches. It is on demand, because the answer is a fresh index of the whole tracked tree: **Check impact** asks for it, and the pane says what it was checked against. Every warning is advice, and nothing it says reaches the plan on its own. **Add to scope** makes it the same mark the Explorer makes, listed in the draft's history with an undo; **Add as a No-Go** appends one line to the spec's No-Gos section, which is the file the Spec pane reads back, and says it once however often you ask. A repository with no tracked TypeScript or JavaScript gets the path classes alone, with a sentence saying nothing there read an import and which extensions it does track; the paths the Explorer withholds never appear here either. Beside whichever pane is open sits the **interview** ([D-102](11-open-decisions.md)): your own Claude Code or Codex session, in a dock that does not collapse, though the bar on its edge drags it wider or narrower — by the pointer, or by the arrow keys once it has focus, with Home returning it to the width it opens at — and what you set it to is remembered on this machine; with the conversation, a line under the last message saying the interview is working for as long as it owes you a word — through the pauses it takes mid-answer, and gone once the next word is yours, or once it has stopped or been stopped ([D-NEW-the-interview-says-when-it-is-working](11-open-decisions.md)), a box to type your turn into and a stop. It reads anything, writes only this spec's folder, `CONTEXT.md` and the ADR folder, and cannot approve, publish or merge; a command it may not run and a write it may not make are each shown as **refused**, with the rule that refused it and nothing to allow or deny — the session is never asked to allow anything and never asks you to. It asks you about the work itself, and what it cannot settle from the repository, the spec or what you have already said comes with the answers to pick from: one group at a time under the conversation, parts lettered together where one answer depends on another, every part carrying the option of leaving it to the interview, and the box below always open for your own words instead — saying something of your own there takes the rest of the questions off the card, since the interview answers what you said, and the line in the conversation that says they were asked keeps them: hover or focus the **i** beside it and they are there. Each of the interview's own cards carries the same **i**, so what a tool wrote is one hover away rather than filling the dock; a refusal shows its reason without asking, because that is the thing to act on. Picking sends the options' own wording as your turn ([D-117](11-open-decisions.md)). A change it makes to the plan goes through the same validated edit path your own edits go through, and shows as a card with what it touched before and after and an **Undo**. **History** opens the plan's every change as a drawer over the pane, so the chat stays where it is: each entry labelled you or the interview, with an undo on the latest still in force. The provider and model are this planning's drafting choice, and the interview is the same interview on either. The conversation is kept with the planning, so leaving planning mode and restarting the app both come back to it, and the interview keeps running until you stop it — sending a turn after that starts it again on the same session, which continues the same conversation. Contract edits in progress are saved on the device and restored if you leave and come back ([D-095](11-open-decisions.md)); the spec's own text lives in the repository instead, and the session remembers which spec it is writing. Planning runs alongside a run: you can draft, save and compile a contract while a loop is going, and while one is going elsewhere. Starting a run, answering a decision, recording a finding, refreshing delivery, recording a product decision and checking a repository each take one at a time, and asking for a second says which one is in the way; disconnecting a repository, deleting a contract or changing its manifest waits for every command running in that repository ([D-101](11-open-decisions.md)).


### The contract editor and approval

The contract shows the outcome, each criterion with its expected evidence, the allowed and prohibited paths, the base commit, the executor and reviewer models, up to three engineering skills for the executor ([D-094](11-open-decisions.md)), and what stops this run — the stall window, the fact that nothing bounds its time, tokens or commands, and the ticket cost cap that applies only to an executor billed per token ([D-096](11-open-decisions.md)). Approving freezes four fields — outcome, criteria, scope, base — for good; how the work gets done stays the agent's. A checkbox asks whether to push the branch and open a pull request once the review gate passes; you still merge it yourself. Approving here is exactly `perbo approve`, run for you before the loop starts. A contract that has never run can be deleted outright; one that has keeps its record.

### The run view and the review result

The loop screen names what's happening now against six stages — contract, execution, checks, decisions required, refinement, review — with a running description of steps taken and a strip of commands used, cost spent and files touched beside the stall window that would stop it; no time estimate is invented. From here you can open the worktree in your editor, stop the loop, or watch the agents' own output: a transcript of executor and reviewer turns, a terminal pane, and the changed files — recorded output, not evidence. The reviewer never reads the executor's narrative.

Once the gate closes, the review screen shows each criterion's verification strength and evidence location, the deterministic checks, and any open findings, with cost and elapsed time beside them; you can send a finding back for another look, export the evidence, or return to the contract to retry. If a pull request was authorized, the merge screen asks one question — merge or don't — with the verified-criteria count, the checks, the scope and the base commit beside it; the desktop opens your browser to GitHub and never merges the pull request itself. Either way the ticket returns you to Home with what changed.

### Completed tickets and the archive

A ticket stays on Home, marked complete, once it merges or closes — nothing files it away on its own. Archiving it, one at a time or all at once, moves it to the Archive: a searchable, filterable, sortable table with a diff column and CSV export, and a ticket filed by mistake returns to Home in one click.

### Settings, shortcuts and themes

The settings icon opens a pill of three sections. **General** holds your name, what can interrupt you and how (below), appearance — light, dark or system; text size; reduced motion — and AFK mode, which holds the machine awake for as long as a run or a decision is live. **Usage** answers whether you can start another ticket: each connected provider's own plan windows where it reports them, and this machine's ledger — spend this month, tickets run and tickets stopped short, average cost per merged ticket — read from retained attempt records, with unpriced attempts marked rather than guessed. **Connections** holds provider sign-in and refresh, default models per role, what stops a run on this machine — the stall window and the per-token ticket cost cap, which can tighten a repository's own limits and never loosen them — and repositories with their environment check and off-limits paths.

Every keyboard binding is rebindable per machine from Settings → General → Shortcuts: click one and press the new combination; a combination already in use is refused and named rather than silently taken. Approving a contract and opening a pull request stay fixed, since they are the two actions that spend money or write to your repository.

Decided, not built: a phone companion once pairing lands ([D-097](11-open-decisions.md)).

### When the loop interrupts you

The loop pauses for you only on a real decision — never for routine progress. One question at a time, with its evidence and, where the executor offered them, a few concrete options plus "let it decide" or your own words in a sentence; every answer stays editable until you confirm the whole set, and confirming resumes the run. Outside a live decision, Perbo only notifies on four things — a decision is needed, a review finishes, a run stops short (it stalled, or hit a ceiling the repository set), or any stage changes — never on progress alone, and never twice for the same fact.

## The same work, from the command line

Everything above has a `perbo` command behind it, for scripting or a repository with no desktop open.

- **`perbo admit`** — one piece of work into a ticket and its contract, in `plan_review`. Type `--outcome`, `--criterion` and `--path` yourself, or let a model draft them from a GitHub issue (`--from owner/repo#412`) or a Markdown file (`--from-file issue.md`) — the same path the desktop's own drafting button uses with what you typed. Nothing runs until the draft is approved.
- **`perbo edit PRB-142`** — open the contract in `$VISUAL`/`$EDITOR`, or pass `--outcome`/`--criterion`/`--path` to change one part directly. Only while the ticket is in `plan_review`.
- **`perbo approve PRB-142`** — freezes the contract from that moment.
- **`perbo run --ticket PRB-142 [--publish]`** — provisions a worktree, executes, seals the change, runs the pinned checks, reviews independently, routes remediable findings back to the executor, and with `--publish` opens the pull request. A person still merges it.
- **`perbo inspect PRB-142 [--attempt <id>]`** — every attempt read back: how it ended, cost, checks, the review and where each finding went; `--verify` recomputes an attempt's stored hashes instead of reading it.
- **`perbo list [--all]`** — the admitted work and where each ticket stands.
- **`perbo sync PRB-142 [--merge]`** — reads the pull request, its checks and its stop answers from GitHub onto the ticket; `--merge` additionally merges it, but only where the repository has opted into `merge: loop` and a separate review run has approved that exact head ([D-041](11-open-decisions.md)).
- **`perbo stops`** — precision of stopping, read live from the answers on pull requests: of the changes with an answer, the share a person endorsed, beside the share of changes a person was shown anything on, and beside it the share of merges that went out unattended.
- **`perbo escapes`** — of the tickets that merged: how many were reverted, and how many separately had a touched path changed again within fourteen days.
- **`perbo serve`** — the queue over the ticket store. Each tick it fetches the base, syncs and, where configured, merges open pull requests in dependency and priority order, starts ready tickets up to the configured concurrency, and drafts tickets from a tracker label if one is configured. While it runs it hosts a local endpoint for your own session.
- **`perbo agent [--provider claude|codex]`** — your own Claude Code or Codex session in the checkout, with that endpoint injected. That session can read every ticket and its evidence, admit new tickets as drafts, edit an unapproved contract, sync a pull request and pause the queue — never approve, publish or merge; that stays a person's keystroke. Needs a running `serve`.
- **`perbo interview --spec specs/<slug>`** — your own session, Claude Code through the Claude Agent SDK or Codex through `codex app-server`, interviewing you about a piece of work and writing the spec. It reads anything and runs read-only commands; the spec folder, `CONTEXT.md` and the ADR folder are the only places it writes, and anything else is refused rather than put to you — on Codex the app server's own approval questions are answered by the same rules rather than reaching you. It drafts the plan from the spec and afterwards changes it only through the validated edit path, recorded as the interview's; it cannot approve, publish or merge ([D-102](11-open-decisions.md)).
- **`perbo principle add "..."`** — records a product answer no established practice could settle; every later executor brief consults it. This is what the desktop's decision screen writes on your behalf when you answer one.

## What you see, and what the loop handles

The loop is the product; independent review is one step inside it, not the thing you interact with directly ([D-088](11-open-decisions.md)). Admitted work runs end to end — execution, checks, review, repair — and a person sees only what needs a decision ([D-001](11-open-decisions.md)). Every finding the executor can close against an established practice, it closes without you; only a `security.*` or `context.*` finding, a deterministic check that failed, the final remediation round, or a point the executor declares it has no practice for reaches you, in the desktop's decision screen or a pull request's checkboxes ([D-065](11-open-decisions.md)). A person picks the model and provider for Perbo's own review ([D-088](11-open-decisions.md)). Decided, not built: reviews other tools leave on the same pull request are read and routed like Perbo's own findings.
