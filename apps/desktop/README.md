# Perbo desktop

A local Electron application over the existing CLI, with a shared React interface and the supplied Perbo artwork. It reads real repositories and records. The sample host in `src/sample-host/` answers the same request protocol from labelled sample records, for the tests and for a development preview in a browser, and the packaged renderer does not contain it ([D-NEW-desktop-sample-host](../../docs/11-open-decisions.md)).

## Run locally

From the repository root, run `./scripts/setup-local.mjs` (or `node scripts/setup-local.mjs` on Windows). It checks Node 22+/npm and Git, uses the repository's pinned pnpm without a global install, installs frozen dependencies, builds the production renderer/CLI and opens Electron. `--no-launch` builds without opening a window. See [Installing Perbo](../../docs/install.md) for provider installation and sign-in. This setup path needs no Vite server. Close an existing Perbo process before launching a rebuilt copy.

For development with live renderer updates:

Prerequisites: Node 22 or newer, pnpm 9.15.9, Git, and either or both subscription CLIs installed and logged in (`claude` / `codex login`). GitHub CLI authentication is needed only for GitHub operations. Login does not guarantee remaining quota.

```sh
pnpm install
pnpm desktop:dev
```

`desktop:dev` builds the CLI, starts Vite on 127.0.0.1:51859 and opens Electron. For a production renderer without a dev server:

```sh
pnpm desktop:build
pnpm desktop:start
```

For a browser-only design preview, run `pnpm desktop:preview`, which opens `preview.html` against the sample host. Add `?empty` to inspect empty onboarding, or `?slow` and start planning from Create to keep simulated drafting and compilation states visible for eight seconds during visual QA. Every screen the preview renders is a reply the sample host answered, the same shape the host answers, so the completion countdown is the app's own three seconds. The app never falls back to sample records when a host request fails: with no adapter in `window.perbo` it says the connection did not load.

## Local package

```sh
pnpm desktop:package
```

The unsigned package is written beneath `apps/desktop/release` for the current host platform and architecture. It bundles the CLI and its guard hook, and runs them on the Node inside Electron (`ELECTRON_RUN_AS_NODE`), so it needs no Node installed on the machine and ships no second interpreter. Git, the provider CLIs and the repository's package manager remain machine prerequisites. Signing/notarization, installer distribution and Windows/Linux runtime qualification are separate release work.

Check the package itself, not only `dist/`:

```sh
node apps/desktop/scripts/check-package.mjs
```

It runs the bundled CLI and loads the Agent SDK through the app's own binary, from inside the package. electron-builder drops a `node_modules` that sits directly under an `extraResources` source whatever its patterns say, so the SDK beside the CLI has an entry of its own, and only a packaged app shows whether it arrived. Run it after any change to how the desktop is packaged.

The `node` development dependency is **not** shipped: nothing copies it into the package. It pins the Node this package's own commands run on, by putting that version on `PATH` ahead of the machine's. Removing it hands the suite to whatever Node the machine has, and a newer one exposes a global `localStorage` that shadows the one jsdom installs, which fails every renderer test at import.

## Test and understand the boundaries

```sh
pnpm desktop:build
pnpm --filter @perbo/desktop typecheck test lint
pnpm --filter @perbo/runner exec vitest run src/codex/index.admission.test.ts src/codex/internal/rpc.test.ts
```

Host integration tests create disposable Git repositories and call the actual bundled CLI for admission, edit, inspect and approval. Coding execution in these tests is controlled. The screens and flows are described in [docs/15](../../docs/15-product-experience-and-onboarding.md).

`src/` is three layers. `host/` is the Electron main process and everything native; `renderer/` is the window; `shared/` is what both read and imports neither. The renderer's own surfaces are `renderer/workspace/` (the bridge and the query hooks over it, with the refresh in `workspace/internal/`), `renderer/contract-editor.ts` and `renderer/shell/route.ts`, which holds the route and what every page is handed. Each test sits beside the module it covers, and `src/renderer/browser-imports.test.ts` is what keeps one out of the app: it bundles the two entries `scripts/build.mjs` builds from and reads the module graph, failing on any `*.test.ts(x)` or `test-support/` input.

The host is a composition root and a module per concern. `src/host/service.ts` builds the modules, wires `ContractEditing`'s IO and answers `request()`; `src/host/routes.ts` is the capability map from a Request kind to the module that answers it, and nothing else. The concerns are `profile/` (the workspace record and the preferences on it), `repository/` (the registry, the paths, `.perbo/config.json`, the store layout and Git), `tickets/` (the reads, the retained output, the exports, deleting and opening one), `plan/` (spec, graph, impact), `interview/`, `jobs/` (the runner and every command's argv), `providers/` (status and usage), and `changes.ts`, `cli.ts`, `explorer.ts`, `symbols.ts`, `power.ts`, `notifications.ts`, `records.ts` and `process.ts` beside them. Every child process starts through `process.ts`'s runner, and the reads of the checkout ask `@perbo/workspace`'s repository module its questions over that runner, so this app spells no git command of its own. Each module's tests sit next to it; the tests whose value is the contract with the real bundled CLI are `src/host/service.e2e.test.ts`, which builds a whole host over a disposable checkout.

The renderer builds on its own primitives in `src/renderer/ui`, shared assets and a closed Zod protocol. Only the host owns native dialogs, validated repository references and fixed CLI subprocesses. A renderer request carries the ids the host needs — a repository's, or a session's where the session's own record names the repository — and, where a surface reads one file, a repository-relative path; it never carries a command, an absolute path or any other filesystem target. The host resolves such a path under the registered repository and refuses it where it is absolute, leaves the repository, passes through a symlink, or may hold a secret, Git metadata or agent configuration. Planning mode's Explorer pane is the surface that reads: it lists the repository's tracked files from `git ls-files`, previews one read-only up to 256 KiB — a larger or binary file is refused with the reason rather than shown in part — and marks a path for the draft's scope or for the repository's standing prohibited list, `paths_prohibited` in `.perbo/config.json`. Planning mode's Spec pane writes the spec into the repository through the host (`specRead`, which carries a session id, and `specSave`, which carries a session id and a repository id; neither carries a path); the host derives `specs/<slug>/spec.md` from the session's slug and the repository's spec folder, and the session records that slug so it opens the same spec again. Between one save and the next the file is the spec, so a spec edited outside the app is what the pane shows when it reads. `Generate plan` and `Start over from the spec…` run `admit --from-spec`, with and without `--start-over`, as `draft` jobs. Planning mode's Graph pane curates the plan's execution graph ([D-100](../../docs/11-open-decisions.md)) through three more requests, each carrying a repository id and a ticket key, plus one `GraphEditSchema` operation for an edit or one edit number for an undo, and nothing a filesystem or a shell could take: `graphRead` assembles the nodes, the order, the size over the repository's tracked files, each node's generated page, the log of every edit, and what the run's own records say about the graph — per node, the sealed change set's paths its globs match, the pinned checks narrowed to it — a run the loop could not narrow is the whole command under the node's name and is not counted — and each criterion as the evidence bindings leave it in the review of the plan the ticket now carries, with whatever the rounds since that review closed taken off it, with the changed paths no node names carried as outside; those records are read straight from `.perbo/state/*.attempts.json` and the bundle store, as `taskSummary` reads them, so a pane refreshed after every edit and while a run moves starts no subprocess, and the executor's transcript and account in the same bundle are read by nothing ([ADR-0023](../../docs/adr/0023-untrusted-context-boundary.md)); `graphEdit` and `graphUndo` run `perbo edit --graph-edit` and `--undo` with `--author`, which is the one path a plan changes through, so the renderer writes neither the contract nor the approach record. The pane's drawing is the desktop's own — placed nodes and an SVG layer of edges, over `graphColumns` — because the content-security policy in `index.html` allows no worker and no remote origin; `src/renderer/planning/GraphPane.policy.test.ts` is what holds that. The sample host answers the same three requests over its sample plans with `@perbo/planning`'s own edit path, so the pane can be driven without Electron and behaves the same when it reaches one. Planning mode's interview ([D-102](../../docs/11-open-decisions.md)) is docked beside whichever pane is open, through three more requests: `interviewStart`, carrying a repository id and this planning's own editing session id; `interviewTurn`, carrying that session's id and the text the person typed; and `interviewStop`, carrying the session's id alone. The session's record names its repository, so the other two need no repository id, and none of the three carries anything else. The host builds the argv from the registered repository and the session's own records — `--repo` from the repository, `--spec` from its spec folder and the slug the session recorded, resolved and refused through `safePath`, `--session` from the id a previous interview reported, and only where that interview ran on the provider this one will, and `--model` and `--provider` from this planning's drafting choice — and spawns the bundled CLI as a long-lived child with stdin open, the one command shaped that way (`startLineProcess` in `host/process.ts`, beside the one-shot `runProcess`), through the same `childEnvironment` and the same redaction. Each stdout line is parsed against `@perbo/contracts/interview-protocol`, which is where the command and the host both read one declaration of it; a line that does not parse is reported as one that did not rather than relayed. Each event becomes a line of the planning session's `conversation`, capped at 400 with the oldest dropped and the cap said on screen, and is pushed to the renderer as an `interview` change; the session id the `started` event reports is recorded on the session, which is what `--session` continues. A turn is validated as a `turn` before it is written down stdin, and a stop ends stdin and signals the process group only for a child still there after that. An `edit_plan` or an `undo_edit` card carries the edit the ticket's `<KEY>.draft.json` recorded rather than the tool's account of it ([ADR-0023](../../docs/adr/0023-untrusted-context-boundary.md)), with an undo on its number. The interview is planning-lane work answered outside the job list, it outlives the pane it was started from and is listed on the snapshot while it runs, and it is stopped when its planning is discarded and when the app closes. Settings is a pill in the rail — General, Usage, Connections — with Shortcuts and About one level under General. General's appearance choices set `data-theme`, `data-text-size` and `data-motion` on the document; the dark palette and the transitions.dev motion tokens and snippets live in `src/renderer/ui` (`tokens.css`, `motion.css`, the latter pinned to an upstream commit named at its top). Usage sums the month's spend from each repository's `.perbo/state/*.attempts.json` and asks Codex's app-server for its plan windows; Claude Code reports none without an inference turn, and the page says so. Completed tickets stay on Home until archived by hand; `archived` is a profile preference, never a Ticket state. The away-from-keyboard hold uses Electron's power-save blocker only while a run or decision job is live. On macOS the native title bar is hidden; the page header is the top bar, beside the traffic lights and a sidebar toggle, and the fixed-width icon rail sits beneath it, hidden or restored from the toggle and remembered per browser profile. Each subscription account on Connections can be refreshed or signed in again; sign-in opens Terminal on the provider's fixed login command through `osascript` with argv only, and the desktop still never takes a credential. Every dropdown is the desktop's own listbox (`Dropdown` in `src/renderer/ui`, the native select's interface over a `t-dropdown` menu), so the OS menu never appears. A contract that has never run — no attempt, no bundle, no pull request — can be deleted from its contract screen; the host removes the ticket's three files from `.perbo/tickets/` and nothing else, and refuses anything with evidence. Claude Code's catalog lists the model its `default` alias points at under that model's own name, marked default, so Opus is never hidden behind the alias. The app keeps its local profile/job journal in Electron's Perbo user-data directory; canonical tickets and evidence remain in each repository's `.perbo` store. Provider CLIs own credentials. Drafting, admission and contract edits run any number at a time, alongside a run; a run, a decision, a finding, a delivery refresh, a product decision and a readiness check take one at a time, and asking for a second is refused naming the one running; disconnecting a repository, deleting a contract or changing a manifest waits for every command running in that repository. Stop signals the command's process group; app restart marks unfinished jobs interrupted.

`src/renderer/ui` is the one home of the renderer's primitives. Import them from `ui/index.js`; `ui/internal/` is its interior. Prefer a shared variant or token to a screen-specific copy, keep control labels accessible when artwork is decorative, and preserve visible keyboard focus and reduced motion.

Model dropdowns use Claude Code's initialization catalog and Codex app-server's paginated [`model/list`](https://developers.openai.com/codex/app-server) metadata. Claude aliases are resolved to model IDs when the CLI provides them. Discovery runs in a temporary directory with repository instructions, hooks, tools and plugins disabled; Codex uses the same isolated credential-only home as execution. No inference turn is sent. The optional Anthropic API reviewer discovers models through `/v1/models` using the app's environment credential. Catalogs are validated, cached for five minutes in the shared query client and manually refreshable. A discovery failure never falls back to a guessed list or silently replaces a saved model. Availability and quota are still checked by the provider when a run starts.

Publication requires the checkbox on that run, and merging is your action on GitHub.
